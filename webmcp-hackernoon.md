# How WebMCP Makes the Web Great Again

*Как WebMCP может вернуть вебу общий язык действий.*

## TL;DR

WebMCP - это не еще один MCP-сервер, который нужно устанавливать для каждого сайта. Это браузерный API, с помощью которого страница описывает свои действия агенту. Человек продолжает пользоваться кнопками и формами, а агент получает компактные инструменты. Главный эффект может быть не в автоматизации кликов, а в экономии токенов и возвращении вебу идеи общей среды.

Проблема современного веба не в том, что в нем слишком много страниц.

Проблема в том, что страницы стали островами.

Можно открыть сайт отеля, прочитать информацию и отправить ссылку. Но если другой сервис захочет использовать поиск, проверку доступности или бронирование, ему обычно понадобится закрытый API, партнерская интеграция или отдельный адаптер.

URL дает доступ к странице. Он не дает автоматического доступа к тому, что эта страница умеет делать.

Пока веб состоял в основном из документов, это было терпимо. Но теперь пользователи хотят поручать агентам задачи, которые проходят через несколько сервисов.

## Веб потерял общий язык действий

У раннего веба была простая суперсила: общие правила. Страницы ссылались друг на друга. Браузеры понимали базовый язык. Любой мог опубликовать документ, а любой другой мог его открыть.

Современные веб-приложения стали намного мощнее, но одновременно стали более изолированными. У каждого сервиса свои кнопки, виджеты, состояния, ошибки, фильтры и бизнес-правила.

Человек может выучить местный диалект сайта. Машине приходится учить его заново.

Отсюда появляются три налога.

Первый - интеграционный. Чтобы связать два сервиса, нужно написать адаптер, разобраться в API, настроить авторизацию и обновлять интеграцию после изменений.

Второй - интерфейсный. Пользователь знает, чего хочет, но должен понять, где сайт спрятал нужное действие. Оно называется «Забронировать», «Продолжить», «Оформить» или находится внутри сложного календаря?

Третий - контекстный. Агенту приходится читать страницу, разбирать ее структуру, смотреть на скриншоты, запоминать предыдущие состояния и повторять действия после ошибки. Пользователь платит за это временем, задержкой и токенами.

WebMCP подходит к этим проблемам с одной стороны: сайт может напрямую описать свои возможности.

## Страница становится поверхностью действий

WebMCP позволяет странице объявлять действия как структурированные инструменты. У инструмента есть имя, описание, параметры и реализация, которая может вызвать существующую логику приложения.

Важна не форма API, а то, кому принадлежит описание действия.

Сайт сам решает, что он умеет. Браузер делает эти возможности доступными агенту. Агенту не нужно сначала восстанавливать смысл страницы через обратный инжиниринг.

Небольшого примера достаточно:

```javascript
document.modelContext?.registerTool({
  name: "add-todo",
  description: "Добавляет задачу в список дел пользователя.",
  inputSchema: {
    type: "object",
    properties: {
      text: { type: "string", description: "Текст задачи." },
    },
    required: ["text"],
  },
  execute: ({ text }) => {
    appStore.dispatch({ type: "ADD_TODO", payload: text });
    return `Задача добавлена: ${text}`;
  },
});
```

Кнопка для человека никуда не исчезает. Визуальная страница тоже остается. У сайта просто появляется еще один способ объяснить ту же возможность.

Это не второй роботский сайт и не обязательно второй backend. Это слой возможностей поверх существующего приложения.

## Один агент, а не новая настройка MCP для каждого сервиса

Обычная модель MCP часто начинается с настройки: добавить сервер, подключить endpoint, выдать разрешения, обновить интеграцию, а потом повторить все для следующего сервиса.

Для backend-системы, которой пользуются постоянно, это может быть нормально. Для всего веба такой подход не масштабируется. Никто не хочет устанавливать и настраивать отдельный MCP-сервер для каждого магазина, календаря, банка, авиакомпании и support-портала, который однажды придется открыть.

Искать MCP для каждого сервиса тоже неудобно. Перед самой задачей пользователю приходится искать подходящий сервер, проверять, можно ли ему доверять, подключать его к агенту и разбираться с разрешениями. Для следующего сайта весь процесс начинается заново.

WebMCP переносит эту сложность на саму страницу. Пользователь открывает сайт, браузер обнаруживает опубликованные им инструменты, а агент использует их в текущей сессии. Пользователю не нужно поддерживать список серверов для каждого сервиса.

Вместо поиска «MCP для этого сайта» достаточно открыть сам сайт. Страница сообщает браузеру, что она умеет, а агент получает эти действия без отдельной настройки на стороне пользователя.

Сайт все равно должен поддерживать WebMCP, а браузер или агент должны уметь с ним работать. Но интеграция становится частью посещения страницы, а не отдельным проектом настройки для каждого пользователя.

## Токены - симптом более крупной проблемы

Экономия токенов - одна из самых практичных причин интересоваться WebMCP.

Сегодня агент часто получает намного больше информации, чем ему нужно. Это может быть разметка страницы, навигация, повторяющиеся подписи, реклама, скрытые элементы, видимый текст, скриншоты и промежуточные состояния. Большая часть контекста не имеет отношения к одному действию, которого хочет пользователь.

Со структурированным слоем действий агент получает компактный список возможностей и точные параметры для каждой. Ему не нужно заново оплачивать токенами изучение всего интерфейса на каждом шаге.

Это может означать:

- меньше разметки и текста в контексте;
- меньше вызовов модели для поиска нужной кнопки;
- меньше повторных попыток после ошибочного действия;
- меньше промежуточных результатов;
- более короткий и дешевый пользовательский сценарий.

Есть важное ограничение. Инструменты тоже занимают контекст. Если сайт опубликует сотни похожих функций с длинными описаниями, он создаст новую версию той же проблемы. Агентскому интерфейсу нужны собственные ограничения: немного четких инструментов, короткие описания, точные параметры и компактные результаты.

Веб всегда оптимизировали под байты, процессор и задержку. Для сайтов, которыми пользуются агенты, в этот бюджет добавляются токены.

Но стоимость токенов остается только видимым симптомом. Глубже лежит отсутствие общего языка действий.

## Что это меняет для человека

Самый интересный сдвиг не в том, что «робот может кликать вместо меня». Интерфейс может стать необязательным для рутинных задач.

Пользователь сможет попросить агента:

- найти подходящее время для записи;
- сравнить товары в нескольких магазинах;
- повторить прошлый заказ;
- заполнить длинную форму поддержки;
- подготовить бронирование и остановиться перед оплатой.

Человеку не придется изучать навигацию каждого сайта. Он описывает результат, а не последовательность кнопок.

Визуальный интерфейс при этом не теряет значение. Он дает контекст, возможность проверить данные, подтвердить действие и забрать управление себе. WebMCP интересен именно тем, что агент может работать в живой сессии пользователя, а не заменять сайт невидимой автоматизацией.

Есть и возможный эффект для доступности. Сложные формы, календари, фильтры и многошаговые сценарии трудно проходить не только AI-агентам. Структурированный слой действий в будущем может использоваться assistive technologies как еще один способ взаимодействия с сайтом.

Это не готовое решение доступности. Но потенциальная аудитория WebMCP шире, чем чатботы.

## Агент становится новым каналом дистрибуции

Поисковики сделали сайты заметными как документы. Агенты могут сделать их заметными как действия.

Старый вопрос:

> Где найти информацию об отеле?

Новый вопрос:

> Какой отель подходит под мои условия и где его можно забронировать сейчас?

В первом случае сайт получает клик. Во втором он может стать частью выполненной задачи.

Это меняет понятие видимости в вебе. Сервису нужно быть понятным не только как источник контента, но и как набор полезных и надежных действий.

WebMCP не создает глобальный поиск действий и не решает координацию нескольких сайтов. Он дает агенту общий способ использовать каждую страницу, которая решила этот слой внедрить.

Но эффект для дистрибуции может быть большим. Сайты начнут конкурировать за то, насколько хорошо агент:

- понимает их возможности;
- завершает их действия;
- экономит контекст;
- сохраняет контроль пользователя.

Новый вопрос SEO может звучать так:

> Агент может найти мою страницу. Но может ли он сделать на ней что-нибудь полезное?

## Новые метрики для продукта

Если действия становятся частью публичного контракта сайта, у продуктовых команд появляются новые метрики.

Придется измерять:

- выбрал ли агент правильное действие;
- были ли параметры корректными;
- сколько токенов стоил сценарий;
- где пользователь забрал управление себе;
- хватило ли результата для следующего шага;
- закончилась ли задача результатом, а не еще одним просмотром страницы.

Конверсия тоже меняется. Успешным визитом может быть не просмотр страницы и не клик по кнопке, а выполненная задача без традиционной сессии браузинга.

Появляется и новый вид тестирования. Инструмент может идеально работать как JavaScript, но плохо работать как интерфейс для модели. Модель выберет не тот инструмент, перепутает два похожих действия, передаст неправильный параметр или вызовет правильные функции в неверном порядке.

Агентским сайтам понадобятся проверки намерений, выбора инструментов, параметров, последовательностей, ошибок и целых пользовательских сценариев.

## Где здесь MCP

WebMCP не заменяет MCP.

MCP полезен для постоянных backend-сервисов, фоновых операций, локальных интеграций и возможностей всего аккаунта. WebMCP полезен, когда агенту нужна живая страница, ее текущее состояние и активная сессия пользователя.

Коротко:

> MCP дает агенту сервис. WebMCP дает ему страницу.

Их можно использовать вместе. Backend предоставляет постоянные операции, а WebMCP открывает контекстные действия внутри текущего сайта.

Для пользователя различие принципиально. Не нужно каждый раз искать MCP, устанавливать отдельный сервер для магазина, календаря или support-портала и заново подключать его к агенту. Совместимый браузер или агент сможет обнаружить инструменты, когда страница открыта.

Инструменты не становятся постоянными глобальными endpoint. Они принадлежат текущему browsing context и исчезают вместе со страницей. Это ограничение одновременно позволяет им работать с актуальной сессией и состоянием.

## Что WebMCP не решает

WebMCP сам по себе не делает сайт безопасным. Сайт все еще должен проверять права, валидировать входные данные, подтверждать важные действия и защищаться от вредного текста в результатах инструментов.

Он также не делает весь интернет автоматически composable. Общий слой появится только у тех сайтов, которые решат его внедрить. Дальше все будет зависеть от браузеров, агентов и того, смогут ли они координировать действия, не отнимая контроль у человека.

WebMCP пока остается предложением для веб-платформы и экспериментальной возможностью браузеров. Это улучшение поверх обычного сайта, а не условие его работоспособности.

## Больший сдвиг

WebMCP легко описать как более надежный способ для агентов нажимать кнопки. Это слишком маленькое описание.

Большая возможность в том, чтобы сайты стали понятны как наборы возможностей. Страница может остаться визуальной для человека и стать структурированной для машины. URL может вести не только к информации, но и к живому набору действий.

Это может уменьшить стоимость интеграций, сэкономить токены, улучшить доступность и сократить путь от намерения пользователя до результата.

А еще вернуть вебу часть исходного обещания: разные сайты могут быть частями одной среды, а не изолированными приложениями, которыми человек обязан управлять вручную.

Так WebMCP и может сделать веб great again.
